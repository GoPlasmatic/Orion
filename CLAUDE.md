# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Orion is a declarative services runtime written in Rust. It exposes business logic management through channels (service endpoints) and workflows (task pipelines powered by dataflow-rs) via a REST API. Ships as a single binary with an embedded SQLite database.

This repo is a cargo workspace (monorepo) with nine crates: `crates/orion-server` (the runtime — everything below describes it), `crates/orion-cli` (the CLI, which has its own `CLAUDE.md`), two shared library crates (`orion-api`, `orion-client`), `crates/orion-definitions` (the static definition primitives — the order-preserving JSON AST, source provenance and the SQL lexer — which the server's `definitions/` and `sql_lex.rs` build on), `crates/orion-extension-api` (the extension surface an edition implements against — the `ChannelDriver`, `ProviderBackend`/`SourceConnectorFacet`, `ConnectionPoolCache` and `PackageVerifier` traits, their contract types (`ConnectorError`/`ConnectorOutput`, the identity newtypes, a read-only `AttemptContext` over the host's `AttemptScope`) and `Registrar`, the registration surface the server's `CompositionBuilder` implements; it depends only on serde, serde_json, thiserror, async-trait and `orion-api` (for `Digest` and `FieldError`), which `extension_api_test.rs` pins), `crates/orion-common` (the runtime's shared primitives, below everything in the server: `config/` (loading and validation, `ORION_SECTION__KEY` overrides, `env://`/`[vars]` references), `errors.rs` (`OrionError` → HTTP response), `crypto.rs` (encoding table, HMAC, Ed25519, the rustls provider), `canonical.rs`, `config_encryption.rs`, `signatures.rs` (the detached `.sig` convention), `metrics.rs` (every Prometheus recorder), `request_context.rs`/`trace_context.rs` (per-request identity, W3C propagation), `http_body.rs` (reading an outbound body under a byte cap **while streaming** — every egress path goes through it), `native_work.rs`, `platform_routes.rs`, `text.rs`, `version.rs`; the server re-exports each under its old `crate::` path, and its `test-support` feature carries the helpers the server's unit tests call), `crates/orion-storage` (the state database, re-exported as `crate::storage`: `DbPool`/`DbTransaction` over the three backends, the embedded `migrations/{sqlite,postgres,mysql}/`, `models/` (row types, DTOs, enums) and `repositories/` (cron, traces, trace_dlq, audit_logs, cluster, shared_state, oauth_state); definitions and connections live in `extensions::deployment_store`, not here), and `crates/orion-plugin-sdk` (the guest crate a plugin author links against — the `orion:plugin` WIT bindings, a `Plugin` trait over JSON and `export_plugin!`; it depends on nothing else in the workspace, carries its own copy of `crates/orion-server/wit/orion-plugin.wit` which `plugin_sdk_test.rs` keeps byte-identical to the server's, and publishes as a rider too). The test fixture (`crates/orion-server/tests/fixtures/plugins/guest`) and the two example guests (`examples/plugins/fixed-width`, `examples/plugins/c4-rules`) are built on it; after changing any of them, the SDK or the WIT, run the `build.sh` beside them and commit the rebuilt component — the `plugin-sdk` CI job rebuilds all three from source and runs the ABI cases (`tests/fixtures/plugins/abi-cases.json`) and the examples' offline cases against the fresh bytes. `crates/orion-api` is the wire contract: response DTOs, domain enums, the error envelope + `codes` registry and the v2 deployment DTOs — the server serializes these types, clients deserialize them; the server re-exports them under their pre-1.0 paths (e.g. `crate::errors::FieldError`, `storage::models::EntityStatus`). Two disciplines, by surface: the operational DTOs that predate v2 (`dto.rs`, `engine.rs` — traces, cron, health, audit, DLQ, engine status, functions) are tolerant (every field defaults, unknown fields ignored, growing vocabularies as strings) so skew between server and CLI keeps working; the v2 admin contract (`orion_api::v2` — `mod.rs` DTOs, `manifest.rs` the deployment manifest and the compiled-deployment files, `vocab.rs` the closed vocabularies) is **strict** — required fields unless absence is documented, `deny_unknown_fields` on requests, enums for closed sets (`ImplementationKind`, `ConnectorErrorClass`, `EffectStatus` and `EditionTier` are defined there and re-exported by `orion-extension-api`), typed sub-structs for server-generated parts, `Value` only for author- or engine-owned documents — because v2 negotiates skew instead: the server reports `v2::API_VERSION` as `RuntimeCapabilitiesResponse.api_version`, and `orion-cli` refuses a server reporting another (`orion_client::check_api_version`) before any `deployments`/`provider`/`connections` command. Bump `API_VERSION` when a v2 change could make the previous client misread an answer or send a refused request (a field removed/renamed/retyped/made required, a request field added, an enum variant an answer carries); an answer gaining a field does not; its `utoipa` feature (enabled only by the server) adds the `ToSchema` derives for the OpenAPI document. `crates/orion-client` is the one HTTP transport over that contract — `OrionClient` (auth, envelope unwrap, typed `ClientError`) plus the `paths` module every endpoint path is built from; `orion-cli` drives it, and it is the only crate that owns reqwest for API calls. None of the seven library crates has a release cycle of its own — no tag names them; `crates-publish.yml` publishes them automatically as riders (skip-if-present, dependency order) right before `orion-server`, because crates.io refuses a crate whose dependency it doesn't host. **All nine crates share one version**, `workspace.package.version` in the root `Cargo.toml`, inherited with `version.workspace = true` and repeated only in the `[workspace.dependencies]` requirements (a path dependency needs a `version` to be publishable). That is what makes the riders safe: a release always moves the number, so skip-if-present can never fire on a rider whose contents changed. Bump it with `cargo release`, never by hand in a member manifest. Note that `orion-server` is the *only* binary crate on crates.io: the `orion-cli` name there belongs to an unrelated 2021 crate, so the CLI ships via the dist installers, the Homebrew tap, GHCR and `cargo install --git` instead (see `RELEASING.md`). `default-members` points bare cargo commands at the server; use `--workspace` or `-p orion-cli` to reach the CLI. Only the UI lives in a separate repo (Orion-ui).

- **Rust Edition:** 2024. **MSRV: 1.98** (`rust-version` in Cargo.toml) — the toolchain the images build on (`rust:1.98-slim` in both Dockerfiles) and the one CI's MSRV job runs the suite against. The MSRV now also tracks [Wasmtime's](https://docs.wasmtime.dev/stability-release.html) (stable minus two), because the plugin sandbox links it, so a Wasmtime upgrade can move the number even when nothing here needs a newer language feature. The *language* floor is lower: let-chains (`if let Some(x) = a && let Some(y) = b`) landed in 1.88, alongside dependency requirements (`serde_with`, `time`, `tonic`).
- **Core dependencies:** `dataflow-rs` 4.0 (the only workflow engine: compilation, validation, the host functions and execution), `axum` 0.8 (HTTP), `sqlx` 0.9 (database), `sea-query` 1.0 (portable SQL builder) with `sea-query-sqlx` 0.9 as its sqlx binder (the crate that replaced `sea-query-binder`; its major tracks sqlx's, so the two move together). sqlx 0.9 dropped the lifetime from `Database::Arguments` and `IntoArguments`, and gated query strings behind `SqlSafeStr` — only a `&'static str` is accepted bare, and anything assembled at runtime must be wrapped in `sqlx::AssertSqlSafe`, which is a deliberate assertion, not a formality: wrap only text Orion itself rendered (a `sea-query` builder, `query::backend::sql`) or the documented raw-SQL escape hatch (`db_read`/`db_write`), never a string with a caller value interpolated into it. dataflow-rs 3.6 made a workflow's `tasks` array hold **steps**: an element carrying a `tasks` key is a task group, and any step may set `terminal: true` to end the workflow. The engine flattens that tree at parse, but Orion's own analysis reads the *authored* JSON — so every walk over `tasks` must go through `engine::walk_steps`/`leaf_tasks` (`engine/steps.rs`) or it silently skips everything inside a group. Both take the workflow's `loop` as well as its `tasks`: since 3.14 a loop's `setup` list holds steps the engine resolves and runs like the body's, and a walk handed `tasks` alone skips them (#351). dataflow-rs 3.15 added `map`'s `"mode": "append"`/`"extend"`, which reads its target as well as writing it; the clippy analysis models that through `dataflow::mapping_keeps_target`, and any new rule reasoning about overwrites must read `StepFacts::reads()` rather than a mapping's `logic` alone. sea-query 1.0 moved the comparison operators (`.eq`, `.lte`, `.is_in`, `.like`, …) off `Expr` and onto the `ExprTrait` trait, so a module building predicates needs `use sea_query::ExprTrait;` — and because that trait is blanket-implemented for everything convertible into an `Expr`, it also makes a bare `.max(…)` on an integer ambiguous with `Ord::max` (spell it `Ord::max(a, b)`).
- **Ask the engine before writing a check about a workflow definition.** dataflow-rs 4 parses (`def::parse`, with `engine::parse_options()`), compiles (`Compiler::compile_one` against the real registry and expression engine, which runs each function's `prepare`) and reports every issue at its authored path with an `IssueCode` and a `Severity`. `engine::compile_row` (`engine/loader.rs`) is the one place a stored row is parsed and compiled, and `engine::quarantines` the one rule for which issues quarantine a channel: every `Rejected`; a `Defect` only for `INPUT_PARSE` (the root-output Defect a function's `prepare` raises) and `LIKELY_TYPO`; never an `Advisory`. A severity a later dataflow-rs adds quarantines until it is classified there. `validation::engine_advisories` reports the rest to authors from the same issues, so the serving screen and the author-facing report cannot disagree. `engine/steps.rs` (the step grammar) and `engine/operators.rs::operator_names` (the live JSONLogic vocabulary, read off a built engine) are thin adapters — do not reintroduce a local copy. The one list Orion keeps itself — `engine::FunctionRegistry` (`engine/functions/registry.rs`), the create-time name gate and the `/admin/functions` catalogue — exists because it is consulted before an engine exists; `function_schema_test.rs` pins it against a live engine. **A host function is a `dataflow_rs::Function`**: a `#[derive(FunctionConfig)]` config compiled at load (a `String` field is a literal required at load; `Interpolated`/`Expr` fields are evaluated per call), `prepare` for checks the config alone cannot make, and `call`. `plugin::PluginFunction` is registered once per manifest function and carries that function's field table, so only the instance knows which fields to validate and which are templates — do not hand a plugin field's template decision to anything keyed by function name.
- **Every definition is parsed strictly: `dataflow_rs::def::parse(json, engine::parse_options())`, the v3 compat reader off.** A v3 spelling (a task's `halt_on`/`continue_on_error`, the function name `validate`, the pre-1.0 input aliases such as `response_path`) and any key a level does not define are Rejected, at create and at load. A new parse site must use `parse_options()`, and a site that reports refusals passes its issues through `engine::name_v3_spellings`, which adds the v4 spelling to write. The workflow-level `continue_on_error` is Orion's own API field (`workflow_json` writes it as `on_failure: continue`) and is not a v3 spelling.
- **`datalogic-rs` 5 (JSONLogic) and `datavalue` are reached through `dataflow-rs`**, not pinned directly. dataflow-rs's public API is written in terms of both — the context/path surface is `datavalue::OwnedDataValue` — so a second pin would let their major versions skew from the ones dataflow-rs links. Add `use dataflow_rs::datalogic_rs;` (or `::datavalue`) to a module that needs them; a bare `datalogic_rs::` path will not resolve, and a file-level `use` does **not** reach an inner `#[cfg(test)] mod tests`. dataflow-rs 4 selects the extension operator families on its `ExprEngineBuilder` at runtime; only `datetime` is a Cargo feature (with `budget`, which enables `engine.ops_budget`); the tensor family is not compiled in. Orion registers its own operators (`src/engine/operators.rs`: base64/base64url/hex encode+decode, `random`, `url_encode`, `url_decode`, `join`) on the one expression engine every generation uses. `docs/src/reference/expressions.md#available-operators` is the resulting vocabulary, asserted against the engine by `jsonlogic_operators_test.rs`.
- **Binaries:** `orion-server` (`crates/orion-server/src/main.rs`) and `orion-cli` (`crates/orion-cli/src/main.rs`)

## Build & Development Commands

```bash
cargo build                        # Build (all features included)
cargo build --release              # Release build

cargo run -- --config ./config.toml  # Run with config file

cargo test                         # Run the server suite (default-members)
cargo test --workspace             # Server + CLI suites — what CI runs
cargo test <test_name>             # Run a single test by name

cargo clippy --workspace --all-targets  # Lint (matches CI)
cargo fmt --all                    # Format code

just e2e                           # End-to-end suite (tests/e2e): CLI against a real orion-server
```

**`just check` is the pre-PR gate** — it runs exactly what the CI PR jobs run, in one command:
`cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo test --doc`, and `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --lib`.
Note the `--workspace` flags: bare `cargo test`/`cargo clippy` only cover the server
(`default-members`), so they silently skip `orion-cli` — CI does not. Other recipes:
`just openapi` (regenerate the committed spec), `just test-containers` (the Docker-gated
suites), `just workflow-tests`, `just docs` / `just docs-preview` (mdbook site), `just fmt`.

**After changing routes or request/response schemas, regenerate the committed spec** —
`cargo run -- dump-openapi > docs/openapi.json` (or `just openapi`). `openapi_test.rs`
fails while it is stale.

Docker: `docker build -t orion .` for the server; `docker build -f crates/orion-cli/Dockerfile -t orion-cli .` for the CLI (both multi-stage from the workspace-root context).

## Runtime Configuration

All capabilities are compiled into a single binary — no feature flags. Behaviour is controlled at runtime:

| Capability | Configuration | Default |
|-----------|--------------|---------|
| Database backend | `storage.url` scheme (`sqlite:`, `postgres://`, `mysql://`) | SQLite |
| OpenTelemetry | `tracing.enabled` | Disabled |
| Trace persistence mode | `trace_storage.mode` (`sync` / `async` / `batch` / `off`) — global default with per-channel override via `config.tracing` | Sync |
| Cron scheduler | `cron.enabled` (an *active* cron channel on a node with it off is quarantined and `components.cron` degrades — never a silent no-op) | Enabled |
| WebAssembly plugins | `plugins.enabled` (off = no Wasmtime engine, no epoch ticker, a plugin definition upload answers `400`, and a deployed plugin is a `disabled` load issue that quarantines its dependants — never an abort). `[plugins.trust]` makes Ed25519 signatures mandatory | Disabled |
| TLS/HTTPS | `server.tls.enabled` | Disabled |
| Swagger UI / OpenAPI spec | `server.docs.enabled` (unset = enabled outside production) | Enabled outside production |
| SQL connectors | `db_read`/`db_write` functions | Always available |
| Cache connector | `cache_read`/`cache_write`/… over an in-process memory backend | Always available |

## Architecture

### Module Structure

Paths below are relative to `crates/orion-server/`.

```
src/
├── main.rs              # clap CLI entrypoint; declares the binary-only cli/signing_cli/sql_cli modules
├── bootstrap.rs         # Startup sequence: config → pools → repos → engine → HTTP server
├── cli.rs               # Diagnostic subcommands: validate-config, migrate, lint, dry-run, test, test-connectivity, dump-openapi
├── sql_cli.rs           # `orion-server sql check` — every `db_read`/`db_write` statement (`definitions::statements`) prepared against a real database as its connector's role, connectors resolved by `connector::resolve_connector_config` (the registry's own sequence); PostgreSQL 16+ proves grants with `EXPLAIN (GENERIC_PLAN)`, each statement in a savepoint of a `READ ONLY` session; `--schema` builds a scratch schema in one rolled-back transaction
├── signing_cli.rs       # `orion-server plugin digest|keygen|pubkey|sign|verify` — produce what `[plugins.trust]` verifies
├── lib.rs               # Public module declarations
├── channel/             # Channel registry, config, routing, rate limiting, request guards
├── cluster/             # Multi-node coordination: `reconcile.rs` (the one cluster loop — the v2 reconciler, which also applies peers' circuit-breaker resets — and the shared-state sweeper), job leases
├── connector/           # Connector types, registry, circuit breakers, pool caching, secret resolution
├── auth.rs              # Admin authentication: the API-key comparison and the per-source failure tracker
├── cron/                # Scheduled channels: the reconciler (schedules -> durable occurrences), the workers (claim -> guards -> `execute_admitted` -> settle), the trigger metadata and the scheduler's own health. The *schedule* is not here — it is authored content on a cron channel, compiled by `ChannelLoader` into `channel/cron.rs`'s `CronDescriptor` and carried on the runtime generation
├── definitions/         # A definition set (channels+workflows+connectors) and the cross-reference pass over it: `lint <dir>` and `compile` share it; shared.rs holds the catalog (`$from` constants, task and value fragments — `FragmentBody` — grounded once by `finish`, which resolves constant→constant and constant→fragment references and poisons cycles), the `$from` splicer and the set's `package` declaration; `expand.rs` is the one scoped walk behind `shared.fragments` (`use`, `$use`, `$each`, `$param`, `{{name}}` — closed lexical scope, cycle/depth/copy limits, and the `SourceMap` entries that let a compiled step be traced to where it was written) (a fourth reserved shared key, told apart from an artifact's `package` by `content_hash`; one per set, closed shape — ids `package.duplicate`, `package.shape`), whose expansion descends into task groups via `engine::is_group` — a flat loop there namespaces only a fragment's top-level ids and leaks the rest into the host workflow

│   ├── analysis/        # Facts every clippy rule reads: flattened steps with reads/writes/certainty (`Reads::uncertain` = a computed or element-scoped read — a rule needing complete reads must then stay silent), every expression compiled by datalogic (`is_constant`, evaluate-against-context), the channel→workflow binding. `operators.rs` classifies every operator as scoping or not; a new operator fails a test until classified
│   ├── fix.rs           # `Fix` — an exact rewrite a rule attaches to its diagnostic — and `apply`: the fold on the source tree and on the compiled form, located by step id (a fragment's or an `$each`'s steps are refused, not edited), proven by recompiling the edited source, then formatted
│   ├── clippy/          # `orion-server clippy`: `Rule` trait + `rules::ALL` registry. No configuration, no suppression — a rule ships only with a proof (`explain()` must say "Proof" and "Silent when") and `tests/fixtures/clippy/<id>/{fires,quiet}/`. │   ├── fmt/             # `orion-server fmt`: style.rs (the numbers + canonical key tables — no user configuration by design), roles.rs (shape classifier; operator nodes by structure, unary/leaf/compound), printer.rs (measure-then-emit, linear). `format_str` re-parses its output and refuses to return a document that differs from the input as a `Value`

│   └── compile.rs       # The authoring layer: an ordered pipeline of `Pass`es (source form → canonical form). A new simplification is a new pass; its `residue()` is what `compile` reports, what the pipeline test asserts empty, and what the admin API refuses by name
├── engine/              # Dataflow engine build, observer, custom function handlers, and `execute_admitted` — the one post-admission step every transport runs
│   ├── steps.rs         # Flattens a `tasks` array of steps (task or task group) — every walk over tasks goes through it
│   └── functions/       # http_call, channel_call, db_read/write, data_query/write, cache_read/write/delete/incr, cache_invalidate, crypto, jwt_sign/verify, connector_call
```

### Startup Sequence (main.rs → bootstrap.rs)

CLI args → config (TOML + `ORION_SECTION__KEY` env overrides, `env://` references resolved after the parse) → `orion::run(config, CompositionRoot::community())` (an edition binary calls it with its own builder) → tracing → metrics → detect DB backend from URL → DB pool + migrations → repositories (cron, traces, trace_dlq, audit_logs, oauth_state) → ConnectorRegistry (empty until the deployment head builds) → HTTP client → plugin sandbox (`WasmRuntime`, only when `plugins.enabled`; `None` makes every stored plugin a load issue on this node) → runtime handle (pre-created around an empty generation, for channel_call) → cache pool → external pool cache (SQL) → node identity + deployment store + revocation ledger + native scheduler → the composition frozen over them (a duplicate registration fails the boot) → custom functions → publish generation 1 (the serving registry, no workflows or channels) → trace queue workers → trace cleanup → DLQ retry → cron reconciler + workers (if enabled) — **the cron workers after the queues, because they produce work that lands in the trace pipeline** → hydrate the deployment store and build the committed head, if any (`engine.fail_on_connector_load_error` refuses the boot when a connection of it did not load) → readiness → v2 reconciler → cluster tasks (in cluster mode the shared-state sweeper) → rate limiter → Axum HTTP server → graceful shutdown on SIGTERM/SIGINT.

### Key Architectural Patterns

- **Channels + Workflows:** Channels are service endpoints (sync/async, REST/HTTP/cron) that link to workflows. A `cron` channel is the one protocol with no caller: it declares a six-field schedule and a fixed payload in `transport_config`, registers no route, and is refused at the HTTP ingress and by `channel_call` — its work reaches the engine only as a claimed occurrence from `cron_occurrences`, or through `POST /admin/channels/{id}/trigger`, which uses the same path. Workflows are task pipelines with JSONLogic conditions. **A node serves exactly its committed v2 deployment** (`extensions::deployment_store`): definitions (workflow, channel, plugin) uploaded by digest (`POST /api/v2/admin/definitions`), connection revisions (`POST /connections`), and a manifest naming them applied under compare-and-swap (`POST /deployments`; rollback is a new revision). A channel member `requires` its workflow; a workflow member `requires` the connections it calls. With no deployment a node serves nothing. A definition set on disk is compiled into a deployment directory by `orion-server compile` and deployed with `orion-cli deployments apply -d`; runnable sets live in `examples/packages/`.
- **Repository pattern:** Trait-based (`CronRepository`, `TraceRepository`, `TraceDlqRepository`, `AuditLogRepository`, `ClusterRepository`, `OAuthStateRepository`) with SQL implementations. Definitions, connections and deployments live in the `ImmutableDeploymentStore` (`extensions/deployment_store/`), not a repository. Traits use `async_trait`. All repos are stored as `Arc<dyn Trait>` in `AppState`.
- **One runtime generation:** the engine, the channel estate and everything compiled against them are **one published value**, `RuntimeGeneration { id, engine, channels, functions, plugins }`, held in an `ArcSwap` behind `Arc<RuntimeHandle>` (`runtime/generation.rs`) and reachable as `state.runtime`. `publish(engine, channels, functions, plugins)` is the only writer and takes every half, so there is no way to store one. **Every ingress loads it exactly once per unit of work** — one HTTP request (`data/mod.rs`, above the route match), one cron occurrence, one queued trace, one `channel_call` — and passes the generation down; `execute_admitted` takes `&Arc<Engine>` from it rather than looking one up. Two loads in a request re-open the bug this closes: while the engine and the estate were two `ArcSwap`s stored one after the other, a request could be admitted by the new estate and executed by the old engine, matching zero workflows and answering `200` with the caller's own input. `concurrency_test::a_reload_publishes_exactly_one_generation` counts the stores.
- **Deployment builds:** `runtime::reconcile_deployment_revision` (`runtime/reload.rs`) reads a committed revision's members from the deployment store, loads the manifest's Connections into the connector registry, builds both halves off to the side and publishes them with one atomic store; the whole sequence is serialised by `AppStateInner::reload_lock` (the only lock in it — `ChannelLoader` has none). A failure while building publishes nothing, so the previous generation keeps serving whole, and the node reports `engine_reload: degraded`. It runs on an apply or rollback (on the node that took it), at boot for the head, and from the v2 reconciler loop (`cluster/reconcile.rs`), which is how every peer converges. Bootstrap's generation 1 and this build are the only two `RuntimeHandle::publish*` callers.
- **Channel estate:** `ChannelSnapshot` (`channel/registry.rs`) is the channel half of a generation — `ChannelRuntimeConfig` per active channel (parsed config, rate limiters, compiled validation logic, backpressure semaphores, dedup stores, response caches), a `RouteTable` for REST route matching, and the quarantine map, all self-consistent (N17). It is an immutable value with no lock and no `ArcSwap` of its own. `ChannelLoader` (`state.channel_loader`) builds the next one from the previous one, carrying unchanged channels over by `Arc` so a reload costs what changed.
- **Host functions:** 15 implement `dataflow_rs::Function`, registered in `engine/handlers.rs::register_functions()` and declared, with their input schemas, in the static tables `engine/functions/schema.rs` converts into `FunctionRegistry::builtin()` — which is the list to check, not this sentence: `http_call`, `channel_call`, `cache_read`, `cache_write`, `cache_delete`, `cache_incr`, `cache_invalidate`, `db_read`, `db_write`, `data_query`, `data_write`, `crypto`, `jwt_sign`, `jwt_verify`, `connector_call`. `connector_call` invokes a v2 connector provider: it runs only inside a served run, on the authority the deployment manifest grants the workflow (`runtime/authority.rs`). `data_query`/`data_write` are the portable read/write dialects (backend-neutral filter + envelope → SQL) in `src/query/`; `db_read`/`db_write` are the raw-SQL escape hatch; `crypto`, `jwt_sign` and `jwt_verify` are self-contained (no connector, no egress), so dry-run executes them for real rather than stubbing them.
- **Composition (extension boundary):** an edition describes what its node serves with an owned `extensions::CompositionBuilder` — `with_edition`, `with_channel_driver`, `with_provider_backend`, `with_providers(|r| …)` (a setup handed the node's deployment store and HTTP options, for providers that need them), `with_resource_pool`, `with_package_verifier` — and passes it to `orion::run` / `bootstrap::assemble(params, composition)`. Bootstrap builds it once into a frozen `Composition` at `state.composition`: plain maps, private fields, a duplicate protocol / `(kind, driver_id)` / pool `cache_id` is an error. Every driver and provider lookup (validation, routing, quarantine, `connector_call`) goes through it. The one mutable part is the `ProviderRegistry`'s **admitted layer**, where `runtime::workflow_providers::sync` registers admitted workflow packages by digest (`admit`/`withdraw`); it can never shadow or remove a composed backend. Revocation is core: the node's `RevocationLedger` is checked by `Admission::verify_package` and before every `dispatch_attempt`, whatever the edition's `PackageVerifier` says. A channel's `protocol` is a string id resolved through the `ChannelDriverRegistry` (there is no protocol enum); `channel::guards::Transport` names core's ingress paths (HTTP sync/async, `channel_call`, cron worker) and their guard rows, not protocols. Provider/pool/source traits are `#[async_trait]`.
- **Connector registry:** Lock-free `ArcSwap<HashMap<String, Arc<ConnectorConfig>>>` for hot-path config reads with secret masking on API reads, and circuit breakers per `(channel, connector)` pairing with zero-allocation borrowed lookups and LRU eviction. Db connector configs carry per-operation gates (`operations: { read, insert, update, delete, upsert, raw_write }`, all default `true`) enforced by the data handlers — e.g. set `"delete": false` to make a connector delete-proof.
- **Trace queue:** `tokio::sync::mpsc` channel with semaphore-limited concurrency for async trace processing (`queue/mod.rs`). Failed traces go to DLQ table with automatic retry.
- **Error handling:** `OrionError` enum in `errors.rs` implements `axum::response::IntoResponse`, mapping variants to HTTP status codes. Returns JSON `{"error": {"code": "...", "message": "..."}}`.
- **AppState** (`server/state.rs`): Central shared state struct. Coherent clusters are grouped into sub-structs (R26): `repos` (`storage::repositories::Repositories` — cron, traces, trace_dlq, audit_logs, oauth_state), and `caches` (cache_pool, sql_pool_cache). Runtime-singular fields stay flat: the composition, the deployment store, the reconciler, the native scheduler, the runtime handle, the channel loader, connector registry, trace/audit queues, config, metrics handle, HTTP client, DataLogic instance, rate limit state, readiness flag, cluster runtime, admin-auth failure tracker, trusted proxies. Passed to all route handlers via Axum's `State` extractor.

### Middleware Stack (server/mod.rs)

1. CatchPanicLayer (outermost — panic recovery)
2. OTel trace context extraction (if `tracing.enabled`)
3. HTTP metrics middleware
4. Admin auth middleware (if enabled)
5. Rate limiting middleware (if enabled)
6. Body limit (max payload size)
7. Compression (gzip/brotli)
8. Security headers (CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, HSTS)
9. Request ID layer (generate/propagate x-request-id)
10. Trace layer (request/response tracing)
11. CORS layer

### Request Processing Flow

```
HTTP Request → Axum Router → Data Route Handler
  → Runtime generation loaded ONCE (engine + channel estate, atomically published)
  → Route Resolution (REST pattern match → channel name lookup → fallback)
  → Channel estate (ingress guards, in order per channel/guards.rs::apply_guards: rate limit, auth, origin, validation, dedup, response cache, backpressure)
  → Engine (generation.engine — the same generation the guards above came from)
    → Channel Router (match by channel name)
    → Workflow Matcher (JSONLogic condition evaluation + rollout bucket)
    → Task Pipeline (ordered function execution)
  → Response (cache store, JSON response)
```

### API Structure

- **Admin** (`/api/v2/admin/`):
  - **Deployments (v2):** `POST/GET /definitions` (content-addressed definitions; upload refuses what would not serve), `POST /definitions/test` (run a workflow definition once, live connectors, nothing stored), `GET /connections`, `GET/POST /connections/{id}/revisions` and `GET /connections/{id}/revisions/{rev}` (immutable revisions; secrets only as `secret_locators`, package dependencies as `bindings`), `POST /connections/{id}/revisions/{rev}/probes`, `POST /deployment-plans`, `GET /deployments` (summaries, cursor-paginated) and `POST /deployments` (CAS on the head; `rollback_to` makes it a rollback; `reviewed_manifest_digest` required), `GET /deployments/{revision}[/convergence]`, connector packages (`GET /connector-packages[/{digest}]`, `PUT …/{digest}/admission`, `POST …/{digest}/revocations`), authoring, `POST /edition-transition-preflight`. Every v2 error code is in the closed `orion_api::V2Code` registry, whose kind sets the status (`v2_error_codes_drift_test`)
  - **Channels:** `POST /channels/{id}/trigger` only — a manual run of a deployed cron channel
  - **Circuit breakers:** `GET /connectors/circuit-breakers`, `POST /connectors/circuit-breakers/{key}` (the reset fans out to every node through the breaker epoch)
  - **Functions:** `GET /functions` — per-function input schemas for tooling
  - **Engine:** `GET /engine/status` — the generation this node serves and its load issues
  - **Cron:** `GET /cron/occurrences[/{id}]` (the durable run ledger), `POST /cron/occurrences/{id}/retry` (another attempt at the same occurrence — same id, same `scheduled_for`), `GET /cron/status` (per-channel cursor, last run, backlog, slots held), `POST /channels/{id}/trigger` (a manual occurrence through the same claim and singleton path)
  - **Cache:** `POST /cache/namespaces/{namespace}/invalidate` — bumps a response-cache namespace's version counter in every store (`channel/cache_namespace.rs`); the workflow form is `cache_invalidate`
  - **Audit logs:** list with filtering; `X-Orion-Change-Context` request header lands in `details`
  - **Backups:** create and list SQLite backups (`VACUUM INTO`, refused in cluster mode). There is **no restore endpoint** — restore is an offline stop/replace-file/start procedure; PostgreSQL and MySQL have no in-product backup and rely on operator snapshot/PITR tooling. See `docs/src/operate/backup-restore.md`.
- **Data** (`/api/v2/data/`): Dynamic handler `/{*path}` — resolves to channel via REST route match or name lookup. Supports sync and async (trailing `/async`). Trace list/get endpoints.
- **Operational:** `GET /health`, `GET /healthz` (liveness), `GET /readyz` (readiness), `GET /metrics`
- **API docs:** `GET /docs` (Swagger UI), `GET /api/v2/openapi.json` — gated by `server.docs.enabled` (unset = served only outside production; 404 when disabled)

### Database

SQLite (default), PostgreSQL, or MySQL — selected at runtime from `storage.url` scheme. All three migration sets are embedded via `sqlx::migrate!()` and the correct set is chosen at startup based on the detected backend (`DbBackend` in `orion-common`, the pools and `migrator_for` in `crates/orion-storage`). `DbPool` is an enum wrapping the concrete pool types (`SqlitePool`/`PgPool`/`MySqlPool`) with dispatch helpers for query execution. Tables: the v2 deployment store (`deployment_revisions`, `deployment_head`, `artifact_objects`, connection revisions, provider packages and admissions, `runtime_nodes`), `traces`, `trace_dlq`, `audit_logs`, the cron ledger (`cron_schedule_state`, `cron_occurrences`, `cron_singletons` — slot 0 of every `forbid` key, addressed exactly as before `concurrency.slots` existed so older binaries contend on the same row — and `cron_singleton_slots` for slots 1 and up) and the cluster tables (`config_epoch` — the circuit-breaker reset fan-out, `job_leases`, `connector_oauth_state`, and `cluster_kv` + `cluster_rate_windows` — the shared dedup store, response cache and rate-limit windows a cluster keeps in its database, judged on the database's clock). Each backend's migrations start at `001_v2_baseline.sql` (`migrations/{sqlite,postgres,mysql}/`); a 1.x database, which carries migrations the baseline replaced, is refused at startup by name rather than upgraded.

**Migration rules** (details in `CONTRIBUTING.md#database-migrations`):

- Shipped migration files are **checksum-frozen** — sqlx records a checksum per applied migration, so never edit an existing `NNN_*.sql`. Add a new numbered file to **each** of the three directories.
- **The three sequences are independent after the shared `001` baseline.** Each backend numbers its own directory, so past `001` the same number can mean different things per backend. **Name migrations rather than number them** in commits, docs and runbooks. `tests/schema_parity.rs` catches a change applied to two backends out of three.
- Write migrations **expand/contract** style: a rolling deploy briefly runs old and new binaries against one database, so a release may only *add* schema alongside code tolerating both shapes; drop the old shape a release later.

## Testing

- **Integration tests** in `crates/orion-server/tests/integration/`: one binary — each file is a module declared in `tests/integration/main.rs`. Use `common::test_app()` which creates an in-memory SQLite DB, full `AppState`, and Axum router. Tests use `tower::ServiceExt::oneshot()` (no HTTP server needed).
- **Test helpers** in `tests/integration/common/mod.rs`:
  - `test_app()` — returns a ready-to-use `Router` with in-memory DB
  - `json_request(method, uri, body)` — builds an HTTP `Request<Body>` with JSON content-type
  - `body_json(response)` — extracts and parses the response body as `serde_json::Value`
- **Pattern for new integration tests:** Clone the app, call `.oneshot(json_request(...))`, assert status, parse body with `body_json()`. See `tests/integration/admin_workflows_test.rs` for examples. Declare the new module in `tests/integration/main.rs`.
- **Other test binaries:** `tests/cluster/` (multi-node contracts), `tests/storage_postgres.rs`, `tests/storage_mysql.rs`, `tests/schema_parity.rs` (container-gated), `tests/metrics_exposition.rs` (isolated for its process-global metrics recorder), plus container-gated modules inside the integration binary listed in `.github/workflows/ci.yml` (kept in sync by `ci_filter_drift_test`).
- **Benchmarks:** `crates/orion-server/tests/benchmark/bench.sh` — 7 scenarios using the `hey` HTTP load generator (`baseline`, `simple`, `complex`, `multi`, `concurrency`, `reload`, `plugin`), plus an opt-in `cluster` scenario that needs the HA compose stack.
- **End-to-end:** `tests/e2e/run.sh` at the repo root — shell suites driving a real server with the CLI binary (`just e2e` locally; the `cli-e2e` CI job). Its data-driven cases split by role: scenario cases in `examples/use-cases/` (each deploys an example package with compile + `deployments apply -d`), runtime-behaviour cases in `tests/e2e/cases/`. An apply replaces the head, so a test needing several services deploys them as one set. The full suite-by-suite map of the test estate is `TESTING.md`.

## Docs and code are kept in sync by tests

A family of drift guards in the integration binary makes the code authoritative and fails
the build when a document disagrees with it. They run in the default `cargo test` — so
these edits are not optional follow-ups, they are part of the change:

| Change | Also update |
|---|---|
| A config field or its `Default` | the section's page under `docs/src/reference/configuration/` + `config.toml.example` (`config_docs_drift_test`) |
| A metric name or label key (`orion-common/src/metrics.rs`) | `docs/src/reference/metrics.md` (`metrics_docs_drift_test`) |
| A task function or its input schema | `docs/src/reference/functions/` — the hub's summary and retry-safety tables plus the function's own page (`functions_docs_drift_test`) |
| A route, method or query parameter | the book's `curl` examples + `docs/openapi.json` (`docs_routes_drift_test`, `openapi_test`) |
| An audit `action` / `resource_type` | `docs/src/operate/audit-logs.md` (`audit_actions_drift_test`) |
| A `FieldError` code | `orion_api::error::field_codes::ALL` (the closed registry) **and** `docs/src/reference/errors.md` — `field_codes_drift_test` also fails on a registered code nothing emits |
| A JSONLogic operator | `docs/src/reference/expressions.md` only — the vocabulary itself comes from `Engine::operator_names()` via `engine::operators::operator_names()`, so registering the operator is all the code needs. `jsonlogic_operators_test` asserts the docs and its evaluated table against the live engine in both directions |
| A workflow-shape rule (task, task group, `terminal`) | `validation/workflows/mod.rs::validate_workflow_tasks_schema` — its catch-all is the engine's own parse and compile (`engine::compile_row`), so a rule the engine already enforces needs no mirror here, only a better message if you want one. Any new walk over `tasks` must use `engine::walk_steps` with the workflow's `loop`, never `tasks.as_array()`, or it skips task groups and `loop.setup` silently |
| A cross-reference check over a definition set | `definitions/check.rs` — one pass, shared by `lint <dir>` and `compile`; give it a stable `check` id so a pipeline can grandfather it |
| An authoring convenience (new source-form syntax) | `definitions/compile.rs` — implement `Pass`, register it in `passes()`, give it a stable id. `residue()` must mirror the rewrite **exactly**: detect more than you expand and the admin API refuses documents `compile` accepts; detect less and source form reaches the runtime. Document it under [Shared definitions](docs/src/reference/cli/shared-definitions.md) — the same section `compile`'s per-pass report and `UNCOMPILED_SOURCE` both name |
| A crate's version | `workspace.package.version` and both `[workspace.dependencies]` requirements, together — `cargo release` does all three; a `version = "…"` line in a member manifest is a mistake |
| The formatter's style (a `STYLE` number, a key table, a layout rule) | `docs/src/reference/fmt.md` (`fmt_style_drift_test`), the fixture pair under `tests/fixtures/fmt/` the rule owns, **and** `examples/` + `tests/e2e/` reformatted in the same commit — `fmt_examples_test` fails otherwise (`just fmt` does it) |
| A function's input field table (order included) | the field table on `docs/src/reference/functions/<name>.md` — `fmt_style_drift_test` asserts the documented order is the registry's, because `fmt` orders inputs by it |
| A clippy rule (new, or its level/summary) | `rules::ALL`, `tests/fixtures/clippy/<id>/{fires,quiet}/` (`clippy_cases_test` refuses a rule without both; `quiet` must trip *no* rule), the table on `docs/src/reference/clippy/index.md` **and** the rule's own page beside it, named after the id with dots and underscores as hyphens (`clippy_docs_drift_test`), and `clippy_examples_test` must stay empty. A rule that attaches a `Fix` also ships a `tests/fixtures/clippy-fix/<case>/{before,after}/` pair (`clippy_fix_test`). Certain-only: `explain()` must name one of the admitted proof sources (engine evaluation, an ingress fact, engine semantics read from source, the registry, structural identity, the `-c` config) and when the rule is silent; a heuristic goes on `docs/src/reference/clippy/not-a-rule.md` with its reason, not in the registry |
| A container-gated test module | the `#[ignore]` name filters in `.github/workflows/ci.yml` (`ci_filter_drift_test`) — a module missing from those lines runs *nowhere*, silently |
| A cron scheduling rule (a misfire policy, the DST behaviour, a `transport_config` bound) | `channel/cron.rs` — the compiler and `plan_pass` are pure and exhaustively unit-tested there, and `validation/cron.rs` is their authoring-time twin. The refused `config` keys and `Transport::Cron`'s guard row are two statements of one decision, pinned to each other by `cron_guards_and_validation_agree` |
| A `crate::` reference from a lower module to a higher one | nothing — `module_layering_test` refuses it. A lower layer needing something from a higher one almost always means the thing itself is in the wrong place; move it down, or add a row to that test's `ALLOWED` with the reason |

## Reading the code: item-ID comments

Around 900 comments across `src/` open with a short code — `N10`, `R13`, `F35`, `W8`,
`S15`, and the `(R26)` referenced above. These are items from the pre-1.0 audits; resolve
one with `git log --grep=N10` (needs full history — `git fetch --unshallow` on a shallow
clone). They are a historical record, safe to ignore when reading or writing code, and
**new comments do not need one**. Two rules: every comment must stand on its own without
its ID, and when a comment's claim stops being true, correct the comment.

## Configuration

See `crates/orion-server/config.toml.example`. All settings have sensible defaults. Environment variables override via `ORION_SECTION__KEY` format (e.g., `ORION_SERVER__PORT=3000`).

### CLI Commands

```bash
orion-server                              # Start server
orion-server -c config.toml               # Start with config
orion-server validate-config              # Validate config (--format summary for a short view)
orion-server migrate                      # Run migrations
orion-server migrate --dry-run            # Preview migrations
orion-server migrate --wait 60s           # Wait for the state database first (retries connection failures only)
orion-server fmt ./definitions            # Format definition files to the house style (--check for CI; one style, no configuration)
orion-server lint workflow.json           # Strict-validate one workflow (--deny-warnings to fail on advisories)
orion-server clippy ./definitions         # Advisory rules beyond lint, only where certain (--list, --explain <rule>; -c for the [vars]/[secrets] rules; --fix applies the fixes a rule proved, each verified by recompiling the edited file; --fix --check prints the diff and writes nothing)
orion-server lint ./definitions           # Validate a whole definition set and the references between its files (a plugin.toml in the tree, or --plugin-dir, makes plugin functions checkable; otherwise they are unverifiable notes)
orion-server dry-run -w wf.json -i in.json --stubs s.json --metadata m.json  # Execute a workflow offline with canned connector replies (--plugin-dir <dir>: plugin functions run for real, never stubbed)
orion-server test examples/workflow-tests # Run offline *.case.json workflow regression tests (--definitions <dir> to resolve $from/use; --plugin-dir <dir> for the components)
orion-server compile ./definitions -o dist/deployment  # Compile a definition set ($from/use resolved, plugin.toml + component inlined) into a deployment directory (deployment.json, definitions/<hex>.json, connections/<id>.json) for `orion-cli deployments apply -d`
orion-server compile ./definitions --format deployment -o dist/deployment  # A revision-free v2 deployment (deployment.json + definitions/<hex>.json + connections/<id>.json); `orion-cli deployments apply -d` deploys it
orion-server test-connectivity            # Probe the state database
orion-server sql check ./definitions      # Prepare every db_read/db_write statement as its connector's role (--connector NAME=URL, --skip-connector, --schema DIR [--database URL --role NAME=ROLE]); executes nothing
orion-server dump-openapi                 # Print the OpenAPI 3.1 spec
orion-server plugin sign plugins/ --key signer.pem  # Sign each component's digest for [plugins.trust] (also digest|keygen|pubkey|verify)
```
